# Build-Rocks Workflow Implementation Plan

**Goal:** Every pull request and every `airsl-cli-v*` release builds, packs and loads both binary
rocks on the five supported platforms before anything is published.

**Architecture:** `.github/workflows/build-rocks.yml` is a hand-written reusable workflow
(`on: workflow_call` with the `plan` input), like `airsl-cli-smoke.yml`. dist calls it as a second
`global-artifacts-jobs` entry, so the job is `custom-build-rocks`:
- it needs `plan` and `build-local-artifacts`;
- `host` runs only if it succeeded or was skipped, so a failed leg stops the GitHub Release;
- under `pr-run-mode = "upload"` it runs on pull requests too (§10.1;
  `probes/190-dist-rocks-global-job.txt`).

No job globs for a rockspec (S20). The workflow's first job, `version`, reads `<version>` from the
plan input: the `app_version` of the plan's one `airsl-cli` release, which dist writes for a pull
request as for a tag (`probes/236-release-version-source.txt` (a)). It checks the plan's JSON types,
the version's shape and both rockspecs' presence in the checkout, with the §5.6.6 messages, and
outputs `version`. Every leg `needs: version` and names both rockspecs exactly,
`crates/airsl-lua/rockspecs/<package>-<version>-1.rockspec`, from `needs.version.outputs.version`.

Each of the five legs of §8.4 builds both packages with `luarocks make`, packs both binary rocks,
loads each from its tree with `crates/airsl-lua/lua/check.lua`, and uploads them as the artifact
`rocks-<arch>`. That name is not dist's `artifacts-*`, so the rocks never reach the GitHub Release
(§9.4).

The legs:
- **Linux:** runs `crates/airsl-lua/ci/manylinux.sh` inside `docker run` of manylinux2014, with
  `<version>` as its third argument (S26). A job-level `container:` cannot run GitHub's node actions
  on glibc 2.17 (M10).
- **macOS:** uses Homebrew.
- **Windows:** uses plan 05's `ci/msvc-lua.cmd` and the official luarocks zip, and also proves the
  Windows `--local` install and the cmd hint on every pull request.

The release workflow is regenerated by `dist generate`, never edited by hand.

**Tech Stack:** GitHub Actions reusable workflows, dist 0.33.1, `actions/checkout@v5`, bash with
`set -euo pipefail` and jq (ubuntu-26.04: bash 5.3.9, jq 1.8.1; locally bash 3.2.57, jq 1.7.1, §1.3),
Docker (`quay.io/pypa/manylinux2014_x86_64`, `…_aarch64`; bash 4.2.46 inside), Homebrew, MSVC,
LuaRocks 3.12.2 / 3.13.0, luarocks-build-rust-mlua 0.2.7, Rust 1.94.

**Content authority:** spec §1.2 S8, S9, S20, S25, S26, §1.3, §2.1 (`build-rocks.yml`,
`ci/manylinux.sh`, `dist-workspace.toml` `global-artifacts-jobs`, `airsl-cli-release.yml`), §2.2
(rows for `ci/manylinux.sh` and `build-rocks.yml`), §2.7 (third bullet), §2.10 M3, M10, §5.6.6,
§5.6.7 (the build-rocks and `manylinux.sh` rows), §6.3 (glibc and macOS floors), §6.4 (the
build-rocks row and the plan-type row), §8.3, §8.4, §9.4 (the steps, pinning, and the
`build-rocks.yml` paragraphs), §10.1, §10.2, §12 R4, R13, R14.

## Order of work

### Task 1 — Write the in-container Linux rock build

**Files:**
- Create `crates/airsl-lua/ci/manylinux.sh`, a bash script run as `bash
  /src/crates/airsl-lua/ci/manylinux.sh /src /out <version>` inside the manylinux2014 image. Its
  shape is `probes/160-ci-probe-src/ci/y1-manylinux.sh`, keeping only the "jit-via54" path: LuaJIT
  is built through the Lua 5.4-hosted luarocks, because a LuaJIT-hosted luarocks could not load the
  backend (§8.4).
  - **Arguments first** (S26, §5.6.6): exactly three, the read-only checkout, the output directory
    and `<version>`. Any other count prints `manylinux.sh: expected 3 arguments (checkout
    directory, output directory, version), got {n}` and exits 1 before anything is built or
    installed. It does not re-check `<version>`'s shape or the rockspecs' presence; the `version`
    job owns both, on the same commit.
  - It runs with `set -euo pipefail` and stops at the first failure.
  - It installs `unzip`/`zip` if they are absent.
  - It installs Rust 1.94 with rustup's minimal profile.
  - It downloads `lua-5.4.8.tar.gz` and `luarocks-3.12.2.tar.gz`. It checks them against
    `4f18ddae154e793e46eeab727c59ef1c0c0c2b744e7b94219710d76f530629ae` and
    `b0e0c85205841ddd7be485f53d6125766d18a81d226588d2366931e9a1484492` and exits non-zero on a
    mismatch.
  - It builds Lua into `/opt/lua54`. It clones LuaJIT at exactly commit
    `96f7b297326e9fd454b7186c6858b2773f94a0dc` and builds it into `/opt/luajit`. It builds luarocks
    against Lua 5.4 into `/opt/lr54`.
  - It copies the read-only checkout to a writable directory and works from that copy (probe 160's
    `cp -r "$SRC" /tmp/repo; cd /tmp/repo`).
  - For `airsstack`, then `airsstack-luajit`, it names the rockspec
    `crates/airsl-lua/rockspecs/<package>-<version>-1.rockspec`, relative to the copy, from the third
    argument; it never globs and never hard-codes a version. `airsstack` runs with `--lua-version 5.4
    --lua-dir /opt/lua54`, `airsstack-luajit` with `--lua-version 5.1 --lua-dir /opt/luajit`. Each
    package goes through:
    1. `luarocks make --tree <tree> <rockspec>`;
    2. `luarocks pack <package> <version>-1` into the output directory;
    3. `check.lua <tree>/lib/lua/<5.4|5.1> <lua54|luajit>` under the matching interpreter.
  - It prints the highest `GLIBC_` symbol version the built `airsstack.so` needs, as the probe did
    (§6.3 floors).
  - A leading comment says what the script is for, its three arguments, and why it runs under
    `docker run` rather than a job container.

**Change:** One script holds the Linux rock build for both architectures, at the version the
`version` job read.

**Proof:** The build is not run locally: `CLAUDE.md` allows no emulated-architecture builds, and
the images are emulated on this machine. Its first build runs are the two Linux legs of the pull
request (R13, R14). Locally, the argument check runs before anything is built, so it can run here
(the form of `probes/248-manylinux-args.txt`):
- `bash -n crates/airsl-lua/ci/manylinux.sh` exits 0;
- `bash crates/airsl-lua/ci/manylinux.sh` prints `manylinux.sh: expected 3 arguments (checkout
  directory, output directory, version), got 0` and exits 1;
- `bash crates/airsl-lua/ci/manylinux.sh /src /out` prints the same with `got 2` and exits 1;
- the same with four arguments prints `got 4` and exits 1.

**Done when:** those four runs give those results, the script carries both §9.4 checksums and the
LuaJIT commit, and `cargo make dod` is green. Commit `ci(airsl-lua): build both Linux rocks inside
manylinux2014`.

### Task 2 — Write `build-rocks.yml`

**Files:**
- Create `.github/workflows/build-rocks.yml`:
  - The header comment, in `airsl-cli-smoke.yml`'s style, says:
    - it is called by dist through `global-artifacts-jobs`, on pull requests and at release;
    - `host` waits for it;
    - it is written by hand, so `dist generate` never touches it;
    - the `version` job reads the version from dist's plan, so no leg globs for a rockspec;
    - the artifacts are named `rocks-<arch>`, not `artifacts-*`, so they are not attached to the
      GitHub Release.
  - `on: workflow_call` with the `plan` input (required string), `permissions: contents: read`.
  - **Job `version`** on `ubuntu-latest` (§5.6.6, S20, S25):
    1. `actions/checkout@v5`, the form `.github/workflows/ci.yml:42` uses;
    2. one bash step, `id: version`, with `set -euo pipefail` and `env: PLAN: ${{ inputs.plan }}`
       (the form of `probes/220-publish-downloads-build-artifacts.txt`:57). Its text is, in order:
       - the `jq -r -s` read and its `case` exactly as §5.6.6 gives them (pasted there from
         `probes/246-release-plan-types/app-version.sh`, where it ran), with their messages:
         `build-rocks: could not read the release plan: jq exit status {code}`, `build-rocks: the
         release plan holds {n} JSON values, not one`, `build-rocks: in the release plan, {where}
         is {what}` (each `{where} is {what}` form of the §5.6.6 table) and `build-rocks: the
         release plan names no single airsl-cli release`;
       - the version-shape test, `^[0-9]+\.[0-9]+\.[0-9]+$`, failing with `build-rocks: the release
         plan's airsl-cli version {version} is not <major>.<minor>.<patch>`;
       - the file test: for `airsstack`, then `airsstack-luajit`, the checkout's
         `crates/airsl-lua/rockspecs/<package>-<version>-1.rockspec` must be a file, else
         `build-rocks: {file} is missing` with that relative path;
       - `version=<version>` written to `$GITHUB_OUTPUT`.

       Every message is printed by this step, which then exits 1.
    3. the job's `outputs: version: ${{ steps.version.outputs.version }}`, the mechanism
       `.github/workflows/airsl-cli-release.yml:51-52` already uses for the plan.
  - **Five legs**, one per runner of §8.4, each with `needs: version`; each checks out the
    repository and names both rockspecs and `<version>-1` from `${{ needs.version.outputs.version
    }}`, interpolated into its script as probe 242's legs did
    (`probes/242-ci-probe-src/.github/workflows/probe.yml`, bash and `cmd`):
    - **`linux-x86_64` (`ubuntu-latest`) and `linux-aarch64` (`ubuntu-24.04-arm`):** the step sets
      `VERSION: ${{ needs.version.outputs.version }}` in its `env:` and runs `docker run --rm -v
      "$PWD:/src:ro" -v "$RUNNER_TEMP/out:/out" <image> bash /src/crates/airsl-lua/ci/manylinux.sh
      /src /out "$VERSION"`, `<image>` being `quay.io/pypa/manylinux2014_x86_64` or
      `quay.io/pypa/manylinux2014_aarch64` (§9.4, the invocation probe 253 ran).
    - **`macosx-aarch64` (`macos-latest`) and `macosx-x86_64` (`macos-26-intel`):** `brew install
      lua@5.4 luajit luarocks`. Then `luarocks --lua-version 5.4 --lua-dir $(brew --prefix lua@5.4)`
      for `airsstack` and `--lua-version 5.1 --lua-dir $(brew --prefix luajit)` for
      `airsstack-luajit`, each running `make --tree` with the named rockspec, `pack <package>
      <version>-1`, and `check.lua` under the matching interpreter
      (`probes/165-y3-brew-macos-arm64.txt`, `probes/166-y3-brew-macos-x86_64.txt`).
    - **`win32-x86_64` (`windows-latest`):** in order:
      1. `ilammy/msvc-dev-cmd@0b201ec74fa43914dc39ae48a89fd1d8cb592756` and
         `crates\airsl-lua\ci\msvc-lua.cmd`;
      2. the luarocks 3.12.2 `windows-64` zip, checked against
         `d3f4ddda6926618cadf560170a7c18a5ceead5997ba10832cd0e3b624c7de886`;
      3. in `cmd`, `--lua-version 5.4 --lua-dir C:\lua54` and `--lua-version 5.1 --lua-dir
         C:\luajit`, each running `make --tree %RUNNER_TEMP%\<tree>
         crates\airsl-lua\rockspecs\<package>-<version>-1.rockspec` (the form of
         `probes/160-ci-probe-src/.github/workflows/probe-ci.yml:164`), `pack` and `check.lua`;
      4. the `airsstack` rock installed with `--local`, then `luarocks path > lrpath.bat`,
         `call lrpath.bat`, and a `require("airsstack")` that must succeed. This keeps the Windows
         hint proven (`probes/221-windows-local-install-path.txt`:922-925, :980).
  - Each leg uploads its two `.rock` files with `actions/upload-artifact` as `rocks-<arch>`, using the
    luarocks arch name (`linux-x86_64`, `linux-aarch64`, `macosx-aarch64`, `macosx-x86_64`,
    `win32-x86_64`). It fails if either file is missing.
  - Each download step checks its §9.4 checksum and fails on a mismatch. It uploads nothing outside
    the run (§10.2).

**Change:** One definition of "build every binary rock", at the version dist's plan names. A
version bump that did not rename the rockspecs stops at the `version` job before any leg, naming the
first rockspec it lacks (§6.4). Once Task 3 wires it in, a broken rock fails the pull request that
broke it.

**Proof:** The first run is the pull request's `custom-build-rocks` job (R14: the rewritten read has
run as a script under the runner's bash and jq, not yet inside this job). It must show the
`version` job writing `version=0.2.0`, then, on each of the five legs:
- "Packed: …<package>-0.2.0-1.<arch>.rock" for both packages;
- both `check.lua: ok` lines;
- on Windows, the `require` succeeding after `call lrpath.bat`.

Locally, before committing:
- the `version` step's script, saved to a scratch file and run from the repository root with
  `GITHUB_OUTPUT` pointing at a scratch file:
  - `PLAN="$(cat .claudestacks/sdlc/2026-11-26-airsstack-native-module-and-rocks/probes/246-release-plan-types/plan-pr.json)"`
    exits 0 and leaves `version=0.2.0` in the output file (probe 246; both rockspecs exist after
    plan 06);
  - `PLAN='{"releases":5}'` prints `build-rocks: in the release plan, releases is a number, not an

  - `PLAN='{} {}'` prints `build-rocks: the release plan holds 2 JSON values, not one` and exits 1;
  - a plan whose `airsl-cli` `app_version` is `0.3.0` prints `build-rocks:
    crates/airsl-lua/rockspecs/airsstack-0.3.0-1.rockspec is missing` and exits 1 (probe 236 (e));

  `python3 -c 'import sys, yaml; yaml.safe_load(open(sys.argv[1]))' .github/workflows/build-rocks.yml`
  exits 0 (PyYAML, already installed with the local `python3`; syntax only, GitHub checks the

- the file has `on: workflow_call` with `inputs.plan`, every leg has `needs: version`, no step

**Done when:** those local runs give those results and `cargo make dod` is green. Commit

## Risks

- This is the riskiest plan for CI time and flakiness: six jobs, two of them building three
  toolchains from source in Docker. A leg failing for an infrastructure reason blocks the release by
  design.
- R14 (spec): the rewritten plan read has run as a script under the runners' bash and jq
  (probe 250) but not inside this job; the job form ran with the round-1 read (probe 242); the
  `version` job has not run inside `build-rocks.yml` called by dist's release workflow with
  `inputs.plan`; `ci/manylinux.sh` has not run in the aarch64 image. The pull request's
  `custom-build-rocks` job is the first run of each.
- `copy_directories` with a `/`-separated path was proven on macOS only (R13, accepted). The Linux
  and Windows legs are its first runs.
- The macOS legs follow Homebrew's current `lua@5.4`, `luajit` and `luarocks`, which are not pinned
  (§9.4). `check.lua` refuses a wrong interpreter.
- Not done here: uploading to luarocks.org (plan 10).

## Proof

- `dist generate --check` and `dist plan` exit 0.
- `cargo make dod` is green.
- On the pull request, the `version` job and all five `custom-build-rocks` legs are green, and each
  leg uploads a `rocks-<arch>` artifact holding two rocks.
