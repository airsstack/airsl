# Publish-Rocks Workflow Implementation Plan

**Goal:** Every non-prerelease `airsl-cli-v*` release uploads both rockspecs and all ten binary
rocks to luarocks.org after the GitHub Release exists.

**Architecture:** `.github/workflows/publish-rocks.yml` is a hand-written reusable workflow that
dist calls as a `publish-jobs` entry (`custom-publish-rocks`):
- it needs `plan` and `host`, so it runs after `gh release create`;
- it is skipped for prereleases;
- `announce` waits for it;
- it gets `secrets: inherit` (§10.1).

It runs on `ubuntu-latest`, whose image ships `curl` and `jq`. Its steps follow §10.3 in order:
1. **check:** the empty-key test, then `<version>` read from the release tag dist hands it in the
   plan (S20), before any download or request; the version leaves this step as a step output;
2. the `rocks-*` download into `rocks/`;
3. the checkout of the tag into `src/`, for its two rockspecs;
4. **upload:** the twelve-file check over names built from `<version>`, then phase 1 (both
   rockspecs through `/upload`, each followed by the root-manifest name check), then phase 2 (the
   ten binary rocks through `/upload_rock/<version.id>`).

Every failure prints its §5.6.4 message and stops the job; `{file}` in every message is the
relative path the job tested or sent (S25). Because the version comes from the tag, every required
file has a name before the download, so a missing rockspec is named like a missing rock. It uses the
luarocks.org HTTP API, because `luarocks upload` sends at most one rock (§2.2). It never packs or
uploads a source rock (S12).

**Tech Stack:** GitHub Actions reusable workflows, dist 0.33.1, `actions/download-artifact@v8` and
`actions/checkout@v6` (the versions probe 220 ran under a publish job's token), bash with `set -euo
pipefail` (ubuntu-26.04: bash 5.3.9; locally 3.2.57), `curl -sS -w '%{http_code}'`, jq 1.8.1
(runner) / 1.7.1 (local), the luarocks.org upload API.

**Content authority:** spec §1.2 S9, S12, S15, S20, S25, §1.3, §2.1 (`publish-rocks.yml`,
`dist-workspace.toml` `publish-jobs`, `airsl-cli-release.yml`), §2.2 (`publish-rocks.yml` row),
§2.10 M3, M15, §5.6.4, §5.6.7 (the publish rows), §6.4 (rows from "re-running a failed publish"
on, the rockspec-absent row, the tag row and the plan-type row), §10.1, §10.3, §10.4, §12 R1, R3,
R14.

## Order of work

### Task 1 — Write `publish-rocks.yml`

**Files:**
- Create `.github/workflows/publish-rocks.yml`:
  - **Header comment**, in `airsl-cli-smoke.yml`'s style. It says:
    - dist calls it after `host`, and skips it for prereleases;
    - the version comes from the release tag, which is the rockspecs' `source.tag` (§2.5), so the
      version uploaded is the version the rockspecs build;
    - it uses the HTTP API because `luarocks upload` sends one rock;
    - the name check, and why it runs after `/upload`: no server answer names an owner before an
      upload (§5.6.4);
    - re-running is safe for every failure but a taken name;
    - the prerequisite: a luarocks.org account without upload two-factor, its key in
      `LUAROCKS_API_KEY` (§10.4).
  - **Trigger:** `on: workflow_call` with the `plan` input.
  - **Job:** one job on `ubuntu-latest` with `env: LUAROCKS_API_KEY: ${{ secrets.LUAROCKS_API_KEY
    }}`.
  - **Steps**, in order:
    1. **check**, `id: check`, one bash step with `set -euo pipefail` and `env: PLAN: ${{
       inputs.plan }}` (the form the publish job of `probes/220-publish-downloads-build-artifacts.txt`
       received, :298):
       - if `LUAROCKS_API_KEY` is the empty string, print `publish-rocks: LUAROCKS_API_KEY is empty;
         add the luarocks.org API key as a repository secret` and exit 1. An undefined secret
         arrives empty (probe 220 :302).
       - the tag read and its `case`, exactly the §5.6.4 "The tag read" block (pasted there from
         `probes/246-release-plan-types/tag.sh`, where it ran), with its messages:
         `publish-rocks: could not read the release plan: jq exit status {code}; nothing was
         uploaded`, `publish-rocks: the release plan holds {n} JSON values, not one; nothing was
         uploaded`, `publish-rocks: in the release plan, {where} is {type}, not {expected}; nothing
         was uploaded` (each form of the §5.6.4 "wrong type" row) and `publish-rocks: the release
         plan names no tag; nothing was uploaded`.
       - the tag-shape test, bash's `[[ $tag =~ ^airsl-cli-v([0-9]+\.[0-9]+\.[0-9]+)$ ]]`; no match
         prints `publish-rocks: the release tag {tag} is not airsl-cli-v<major>.<minor>.<patch>;
         nothing was uploaded` and exits 1; the group is `<version>`.
       - `version=<version>` written to `$GITHUB_OUTPUT`, read by step 4 as
         `steps.check.outputs.version` (the step-output mechanism
         `.github/workflows/airsl-cli-release.yml:51-52` already uses).
    2. `actions/download-artifact@v8` with `pattern: rocks-*`, `merge-multiple: true` and `path:
       rocks/` (the form probe 220 downloaded with into `dl-c/`,
       `220-publish-path-src/.github/workflows/publish-rocks.yml`).
    3. `actions/checkout@v6` with `path: src` and no other input, so the release tag (the run's ref)
       lands in `src/` (the form probe 220 checked out with into `co`, same file :66-71). It works
       under the publish job's token (probe 220 :553).
    4. **upload**, one bash step with `set -euo pipefail`, `<version>` taken from
       `steps.check.outputs.version`, which:
       - requires all twelve files, in this order (§10.3 step 4): for `airsstack`, then
         `airsstack-luajit`, the rockspec `src/crates/airsl-lua/rockspecs/<package>-<version>-1.rockspec`,
         then the five `rocks/<package>-<version>-1.<arch>.rock` in the §8.4 order
         (`linux-x86_64`, `linux-aarch64`, `macosx-aarch64`, `macosx-x86_64`, `win32-x86_64`). The
         first one missing prints `publish-rocks: {file} is missing; nothing was uploaded` and exits
         1 before any request;
       - runs **phase 1** for `airsstack`, then `airsstack-luajit`: `POST /api/1/<key>/upload` with
         `rockspec_file`. It reads `version.id` with `jq -e '.version.id | numbers'`, then checks
         `jq -e '.manifests | any(.name == "root")'`;
       - runs **phase 2**, once phase 1 passed for both: for each package, `POST
         /api/1/<key>/upload_rock/<version.id>` with `rock_file`, for each of its five rocks.
  - **Requests:** every request is `curl -sS -w '%{http_code}' -o <body file>`. curl's exit status is
    the transport; the printed code is the HTTP status. The step maps outcomes to the §5.6.4 texts,
    exactly:
    - **transport:** curl exits non-zero, giving `publish-rocks: could not reach luarocks.org to
      upload {file}: curl exit status {code}`.
    - **HTTP refusal:** a code outside 200–299 gives `publish-rocks: luarocks.org refused {file} (HTTP
      {code}): {response body}`.
    - **no version id:** a 2xx whose `.version.id` is not a number, including a non-JSON body (jq exit
      5), gives `publish-rocks: luarocks.org answered {file} without a version id: {response body}`.
    - **name owned elsewhere:** no `root` manifest gives `publish-rocks: luarocks.org did not put
      {package} in its root manifest, so the name {package} belongs to another account; no binary
      rock was uploaded for either package`. No phase 2 request is sent.
  - **`{file}`** in every message is the path tested or sent, relative to the job's working
    directory: `src/crates/airsl-lua/rockspecs/<package>-<version>-1.rockspec` for a rockspec,
    `rocks/<package>-<version>-1.<arch>.rock` for a binary rock, never a base name alone (S25).
  - **Partial state:** the step keeps an ordered list of files uploaded so far. When any of the last
    four failures follows an earlier successful upload in the same run, it adds the line
    `publish-rocks: uploaded before this failure: {files, in upload order}; re-running the job
    replaces them`, the files in the `{file}` form joined by `, `. A name refusal lists its own
    rockspec there.
  - **Key:** the key never appears in a printed line, only in the request URL.

**Change:**
- At release, both packages' versions are created from their rockspecs, and all ten binary rocks are
  attached, under the version the tag names.
- A plan or tag the job cannot read a version from stops it before the download; a missing file,
  rockspec or rock, stops it before any request.
- A taken name fails before any binary rock, on the first run and on every re-run (§6.4).
- Any other failure can be fixed by re-running, because uploads replace in place.

**Proof:**
- No local run uploads anything; the first real run is the roadmap's release (§10.4, R14). Locally:
  - the check step's script, saved to a scratch file, run with `LUAROCKS_API_KEY=x` and
    `GITHUB_OUTPUT` pointing at a scratch file (the form of probe 246's driver):
    - with `PLAN` the contents of
      `.claudestacks/sdlc/2026-11-26-airsstack-native-module-and-rocks/probes/246-release-plan-types/plan-tag.json`
      it exits 0 and leaves `version=0.2.0` in the output file;
    - with `plan-pr.json` it prints `publish-rocks: the release tag v0.2.0 is not
      airsl-cli-v<major>.<minor>.<patch>; nothing was uploaded` and exits 1;
    - with `PLAN='{"announcement_tag":5}'` it prints `publish-rocks: in the release plan,
      announcement_tag is a number, not a string; nothing was uploaded` and exits 1;
    - with `PLAN='{} 5'` it prints `publish-rocks: the release plan holds 2 JSON values, not one;
      nothing was uploaded` and exits 1;
    - with `PLAN='{}'` it prints `publish-rocks: the release plan names no tag; nothing was
      uploaded` and exits 1;
    - with `LUAROCKS_API_KEY=` it prints the empty-key message and exits 1 before reading the plan;
  - the two jq tests are the ones §5.6.4 cites, run against the probe's fixtures:
    - `jq -e '.manifests | any(.name == "root")'` on `probes/234-publish-jq-checks/in-root.json`
      prints `true` and exits 0;
    - on `taken-first.json`, `taken-rerun.json` and `other-manifest.json` it prints `false` and
      exits 1;
    - `jq -e '.version.id | numbers'` exits 4 on `id-string.json` and `no-version.json`, and 5 on
      `html.txt` (`probes/234-publish-jq-checks.txt`);
  - `bash -n` on the upload step's script, saved to a scratch file, exits 0;
  - the file is valid YAML:
    `python3 -c 'import sys, yaml; yaml.safe_load(open(sys.argv[1]))' .github/workflows/publish-rocks.yml`
    exits 0 (PyYAML with the local `python3`; syntax only).
- A read-through against the §5.6.4 table and §10.3 step 4 confirms each message, the `{file}` form
  and the order of the twelve names.

**Done when:** the runs above give those results and `cargo make dod` is green. Commit `ci: upload

## Risks

- This is the riskiest plan in the set to leave unexercised: its first real run is the roadmap's
  release. Each piece is proven separately (§10.3: the API shapes in probes 189 and 231, the
  download and checkout in probe 220, the jq tests in probe 234, the tag read in probes 236, 242,
  246 and 250), but the combined job is not, and this plan cannot run it without uploading. R14
  (spec): the tag read has not run on a plan from a real tag push.
- R1: the names could be taken before the release. The job then fails with the name message on every
  run. If `airsstack-luajit` is the one refused, `airsstack`'s rockspec has already created its
  version without binaries.
- R3: between the first `/upload` and the last binary upload, an install of that version builds from
  source.
- Prerequisite, not code: the `LUAROCKS_API_KEY` secret and an account without upload two-factor
  (§10.4). Plan 12 lists them for maintainers.

## Proof

- `dist generate --check` and `dist plan` exit 0.
- The check step's local runs and the jq fixture runs give the probes' results.
- `cargo make dod` is green.
