== 7. What these citations establish, and what stays unproven (nothing was built or run on Windows by this probe)
- mlua-sys 0.11.0 module mode on Windows links each Lua C API function with #[link(name = "lua54"|"lua51", kind = "raw-dylib")]
  (section 1 lines 29-36, section 3): no import library and no Lua headers are needed at build time; the DLL must be named
  lua54.dll (Lua 5.4) or lua51.dll (LuaJIT, which uses the lua51 bindings) and be loaded in the host process at run time.
  A non-empty LUA_LIB_NAME switches to an ordinary rustc-link-lib against that library instead (section 2).
- mlua's own CI at v0.12.0 runs Windows module tests only under MSYS2 with mingw-w64-x86_64-rust, i.e. x86_64-pc-windows-gnu,
  for lua55, lua54 and luajit (section 5, lines 200-219). The x86_64-pc-windows-msvc target appears only in the Build and Test
  jobs, which do not build module mode. So no mlua CI job builds or loads an MSVC module.
- Unproven: that an x86_64-pc-windows-msvc build of the module loads in any real Windows Lua 5.4 or LuaJIT (which DLL names
  and CRTs those distributions ship, e.g. lua54.dll vs lua5.4.dll, and whether LuaRocks' Windows Lua exports from lua54.dll);
  that Neovim on Windows exposes lua51.dll to modules. A Windows cross-compile probe here was started and stopped on the
  coordinator's instruction (host overload); Windows is to be proven on a GitHub Actions windows runner by another agent.
